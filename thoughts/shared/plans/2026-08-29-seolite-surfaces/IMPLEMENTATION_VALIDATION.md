## 3. Failure & concurrency handling

- **Worker per-request composition (E13):** Confirmed stateless — `worker/index.ts:46,33,36` construct `mcpComposition`/`restComposition` fresh on every `fetch()` invocation; `cappingFetcher` (`composition.ts:49`) is a module-level *stateless* wrapper (holds no per-request data, only wraps the pure `fetch` call), which is consistent with "nothing is shared except read-only code" (Design Analysis, PLAN.md:115).
- **History promise-queue mutex + O_APPEND (E13/B6):** Not touched by this diff (JsonlHistoryStore itself is Phase 2), but its guarantees are newly *exercised* under real concurrency by this diff's Phase 6 tests: `concurrency.test.ts` (in-process, single instance, tests the promise-queue path) and `history.test.ts:176-223` (25 separate instances sharing one file, tests the O_APPEND cross-process-simulated path). Both pass with 25/25 intact lines and no torn writes.
- **SIGINT mid-audit contract (E14):** Verified as a *real* signal delivery test, not a mocked AbortController — `cancellation.test.ts:97` calls `process.kill(process.pid, 'SIGINT')` against the actual running `run()` call. This is a stronger test than the plan strictly required and correctly exercises the real `process.on('SIGINT', ...)` path in `run.ts`.
- **`lumen mcp` shutdown resolvability (E14):** The documented SDK bug workaround (`StdioServerTransport.close()` only pauses stdin; `mcp.ts:65` destroys stdin on abort) is load-bearing — without it the abort path would hang. REASONING.md states this was verified against the installed SDK's `dist/esm/server/stdio.js` source. I did not independently re-verify the SDK internals, but the spawn test (`mcp-shutdown.test.ts:91-103`) exercises the real compiled binary with a 10s bounded timeout and asserts exit 2 — this is an end-to-end proof, not just a unit-level claim, and is convincing on its own.
- **Cross-transport error mapping:** MCP tool failures map to `isError:true` results (`typedError`, `server.ts:62-69`); REST failures map to the single JSON envelope (`rest.ts:34-43`); CLI failures map to exit 2 (`run.ts:36-53`) — all three surfaces handle the same underlying `LumenError`/provider-failure shape consistently.
- **Oversized upstream (Worker):** Both the up-front Content-Length rejection and the mid-stream abort paths are unit-tested with a controlled `ReadableStream` that proves the body is never drained past the cap (`capping-fetcher.test.ts:14-29,31-63`) — matches the I6 edge requirement precisely ("rejected with guidance to use the CLI, not attempted until timeout").

No gaps found in this charge area beyond the E10 kill-switch scope noted in §2 (which is a plan-level gap, not an implementation-level failure/concurrency defect).

- **Off-by-one / bounds:** `LIMIT = z.number().int().min(1).max(50).default(20)` matches the plan default (20, max 50) exactly (`schemas.ts:24`); `maxPages` bound `1..10_000` matches R3's clamp; REST `limit` param manually re-validates the same `1..50` range (`rest.ts:154`) — consistent duplication (REST can't share the Zod schema, correctly re-implements the same bound).
- **Resource leaks:** `cappedBodyStream`'s `pull()` correctly cancels the underlying reader (`.cancel().catch(() => {})`) both on overrun and on stream cancel (`capping-fetcher.ts:43,49-51`) — no dangling reader lock.
- **N+1 / unbounded work:** `lumen_keyword_ideas` and `lumen_authority` fan out to `Promise.all` over provider arrays with per-provider try/catch (`server.ts:225-234,343-350`) — bounded by the (small, config-driven) provider list, not user input.
- **Scope creep:** None observed — no extra commands, tools, routes, or config surfaces beyond the locked set. `packages/mcp/package.json` scripts match exactly what Phase 5's Success Criteria require (`test`, `test:worker`, `build:worker`, `check:size`, `typecheck`).
- **MaxListenersExceeded in the 25x-concurrent test:** Documented as cosmetic in REASONING.md (25 in-process `run()` calls each register their own `SIGINT` listener; real CLI usage is one process = one listener). I agree this is not a production defect — `run.ts:64,83` correctly registers/deregisters one listener per call via `finally`, so listeners are cleaned up; the warning is purely Node's default-limit heuristic under artificial concurrent test load, not a leak (each listener call `process.off` in `finally`).
