**VERDICT: PASS** (re-validation 2026-09-28 after in-place amendment; initial review against main @ e252c49 was MINOR-FAIL — see F1–F5 below and the Re-validation section at the bottom)

The approach, phase structure, conventions, and AC mapping are sound; every Current State claim checked out at its cited line. But 5 Important findings — two silent-correctness traps whose stated success oracles would **not** catch them (F1, F5), one unfulfilled spec closure (F3), one enumeration gap in the "gates move together" invariant (F4), and one mis-named mechanism (F2) — require a plan amendment before implementation. ## Important findings

### F1 — `init`'s written `byok` map can poison every provider command, and the Phase 1 oracle cannot catch it
- Plan Phase 1 (`PLAN_B2_first_run.md:53`): "`byok` = the 3 default env names … all values sourced from core/provider constants". The natural constant is `DEFAULT_BYOK_ENV_NAMES` (`packages/cli/src/cli-config.ts:28-32`) — keyed **`psi|crux|opr`**, not provider names.
- `nodeComposition` passes `config.byok` to `createProviderRegistry` (`packages/cli/src/composition/node.ts:59`), which rejects byok keys that are not builtin provider names (`packages/core/src/registry.ts:74-81`). Builtin names are `google-suggest, wikipedia-demand, pagespeed, crux, openpagerank, tranco, ddg-serp` (`packages/providers/src/builtins.ts:10-17`) — `psi` and `opr` are **not** among them.
- Consequence: after `lumen init` writes `{byok:{psi:…,crux:…,opr:…}}`, **every buildDeps command (audit/report/keywords/rank/authority) exits 2** with `unknown provider name "psi"`.
- The Phase 1 criterion (`PLAN_B2_first_run.md:59`) asserts only "re-loadable by the real loader" — `loadConfig` accepts any object root and treats `byok` as an open map (`packages/core/src/config.ts:106-123,197-211`), so the toxic file **passes** the stated oracle.
- Fix: write byok keyed by **provider name** with env-name values from `BYOK_ENV_VARS` (`packages/providers/src/config.ts:26-30`: pagespeed→LUMEN_PSI_KEY, crux→LUMEN_CRUX_KEY, openpagerank→LUMEN_OPR_KEY; exported from the barrel). Strengthen the oracle to a registry round-trip (e.g. unit test constructs `nodeComposition(config)` on the re-read file, or the spawn test also runs `config show` + one deps command).

### F2 — `byokReady`/`effectiveByok` do not support doctor's per-provider status derivation on defaults-only configs
- Plan Approach (`PLAN_B2_first_run.md:33`): doctor derives readiness from "effective provider set + `byokReady`"; Phase 2 (`:67`): "`byokReady`-style env check".
- `byokReady` (`composition/node.ts:51-56`) returns **true** when the provider has no declared byok entry ("no key requirement declared — provider decides"). On a clean machine (no config → `DEFAULT_CONFIG.byok = {}`, `core/src/config.ts:81-88`) `effectiveByok`'s fallback map is keyed psi/crux/opr (`cli-config.ts:35-38`), so `byokReady(config,'pagespeed')` → `byok['pagespeed']` undefined → **true**: doctor would report pagespeed `ready` with LUMEN_PSI_KEY unset.
- This violates PRD AC (`thoughts/shared/specs/2026-09-28-lumen-next-features-prd.md:219` — clean machine, no keys → doctor "names all 3 missing env vars with URLs") and spec I3.
- Correct mechanism: `envName = config.byok[provider] ?? BYOK_ENV_VARS[provider]` — i.e. `resolveEnvVar` (`providers/src/config.ts:58-65`, barrel-exported) + `process.env` check. The Phase 2 Local criterion ("no-keys fixture … naming all 3 missing env vars") **would** fail a naive byokReady implementation, so this self-corrects at test time — but the plan must name the right mechanism instead of the wrong one.

### F3 — Signup-URL constants the spec explicitly deferred to "plan Phase 1" are not pinned
- Spec closure table (`IMPLICIT_SPEC_B2_first_run.md:38`): "Exact signup URLs for the 3 keys → **Pinned constants in plan Phase 1**"; bounding assumption `:31` "pinned in code as constants".
- The plan (`:53`) gives descriptions only ("PSI/CrUX Google Cloud console API pages, OPR openpagerank.com") — no literals. Three exact strings remain TBD-by-another-name (and PSI vs CrUX are two distinct console API-library pages). Pin the exact URLs in the plan text.

### F4 — `run.ts` dispatch is missing from every Changes list
- New commands require `case 'init'` / `case 'doctor'` in the dispatch switch (`packages/cli/src/run.ts:87-112`, whose `default: never` is the exhaustiveness guard) — the actual wiring without which the commands throw `unhandled command`.
- Phase 1/2 Changes enumerate args.ts + help.ts (+ composition "only if needed") and Phase 3 enumerates every contract file — but never `run.ts`. TypeScript's never-check backstops this at typecheck, yet I1 ("all gate files enumerated in Phase 3 with the commands") claims exhaustive same-change enumeration; the one file that makes the commands exist is absent. Add it (and note `POSITIONALS`/`OPTIONS` Record entries in args.ts are compiler-forced).

### F5 — I6's engines source is wrong for the shipped artifact, and I6 maps to no failing criterion
- Plan (`:37`): engines "read from root `package.json` via `createRequire`/fs in cli". The monorepo root (engines `>=22`, `package.json:12-14`) is `private: true` and **not shipped** (`packages/cli/package.json` `files: ["bin","dist"]`; npm always includes the package's own package.json). The published package declares its own **`>=22.7`** (`packages/cli/package.json:10-12`) — a different number.
- Reading "root package.json" works only inside the repo; installed, it is absent → the node section breaks or misreports. Read the CLI package's own package.json (works in both contexts, and honestly surfaces the pre-existing `>=22` vs `>=22.7` inconsistency).
- Also: no success criterion exercises the node section at all — I6 is the one invariant with no test that would fail on violation. Add one (fixture asserting the reported engines requirement equals the read value).
