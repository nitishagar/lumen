## Important findings

### F1 — `dist/mcpb/manifest.json` sits under a gitignored path; the anti-drift test and the release job both read it from the checkout
- **Locations:** `PLAN_B1_release_train.md` Approach ("Artifacts are repo-root files (single source of truth for the release workflow)") vs Phase 3 Changes (`dist/mcpb/manifest.json` + `dist/mcpb/README.md`); `/home/nitish/repos/learn/lumen/.gitignore:3` (`dist/`); Phase 3 Local criterion (`npx vitest run test/onboard-artifacts.test.mjs` → "artifacts exist"); Phase 5 `mcpb` job (`npx -y @anthropic-ai/mcpb pack dist/mcpb lumen.mcpb`).
- **Why it fails:** `dist/` is gitignored. The plan says the manifest+README "land" in Phase 3 alongside `test/onboard-artifacts.test.mjs`, which reads `dist/mcpb/manifest.json`. A normal `git add` silently skips them: (a) `npm test` / `npm run validate` goes red on every fresh checkout and in the `build-and-test` CI job (test reads a missing file → ENOENT); (b) the release `mcpb` job packs from a checkout that does not contain the manifest, so the bundle cannot be built; (c) the print-payload constants cannot durably mirror a non-committed file, defeating the anti-drift oracle. The plan's own Approach sentence ("artifacts are repo-root files") contradicts the Phase 3 path.
- **Fix (plan amendment):** move the bundle source to a committed path (e.g. `mcpb/manifest.json` + `mcpb/README.md`, matching the repo-root claim), or explicitly add a `.gitignore` exception (`!dist/mcpb/`) and say so; update the pack command and the test path accordingly.

### F2 — the never-embeds sentinel cannot pass on the new payloads; the plan claims green without specifying the adaptation
- **Locations:** `PLAN_B1_release_train.md` Phase 2 Changes ("never-embeds-key iteration over the new targets") and Phase 2 Local criterion ("14 payload cases pass"); Testing Strategy ("no secrets in artifacts (never-embeds over 14 payloads)"); spec `IMPLICIT_SPEC_B1_release_train.md` I2; code: `/home/nitish/repos/learn/lumen/packages/mcp/src/onboard.test.ts:29-34` and `/home/nitish/repos/learn/lumen/packages/cli/src/mcp-print.test.ts:49-55` — both use `expect(payload).not.toMatch(/KEY|SECRET|TOKEN|sk-/i)`; Phase 2/3 define the `registry` payload as the pretty-printed `server.json`, which necessarily contains `environmentVariables[].name: LUMEN_PSI_KEY|LUMEN_CRUX_KEY|LUMEN_OPR_KEY` (matches `KEY`) and `"isSecret": true` (matches `SECRET`).
- **Why it fails:** extending the TARGETS loops to 7 automatically runs the new payloads through the existing sentinel, which trips on the env-var *names* and the `isSecret` flag — exactly the fields I2 mandates. The plan asserts those tests pass without naming the adapted oracle. A stranger either stalls or lazily weakens the regex (dropping `KEY` would gut the guard for every existing target too).
- **Fix (plan amendment):** specify the adapted sentinel in Phase 2 — e.g. allowlist the three locked env-var names from `locked-names.json` and assert no value-shaped assignment (`/(PSI|CRUX|OPR)_KEY\s*[:=]\s*\S/` absent), or assert only that the *values* of those vars never appear while names are expected. State it for both `onboard.test.ts` and `mcp-print.test.ts`.

### F3 — the mcpb manifest is under-specified (`entry_point: …` elided) and its packability is never verified, though it could be offline
- **Locations:** `PLAN_B1_release_train.md` Phase 3 (`server {type: node, entry_point: …, mcp_config {command: npx, args: [-y, @lumen-seo/cli, mcp]}}`); What We're NOT Doing ("`@anthropic-ai/mcpb` is used only in the release workflow (npx), not in devDependencies"); Phase 3 Success Criteria (no pack check); Design Analysis names the registry job as "riskiest (untestable offline)" but the mcpb job is silently treated the same way despite being testable.
- **Why it fails:** (a) `entry_point` is elided with `…` — a stranger cannot fill it in from the bundle: the P-Thin bundle contains no code file, yet a node-type local server in the mcpb manifest points at an entry file inside the bundle, and `mcpb pack` validates the manifest; a manifest+README-only bundle may be rejected at pack time, discovered only on the owner-gated first tag run. (b) The spec's bounding assumption ("keys entered in Claude Desktop reach lumen as env vars per mcpb `user_config`") is asserted, but the shown `mcp_config` has no env mapping — if the user_config→env delivery requires explicit `${user_config.*}` interpolation in `mcp_config.env`, FR-2's P-BYOK promise silently breaks. (c) `npx -y @anthropic-ai/mcpb pack` runs without adding a devDependency, so a Local/E2E criterion "pack succeeds" was available and is missing — Phase 3's only verification is the JSON-shape test the plan wrote itself.
- **Fix (plan amendment):** pin the exact manifest JSON (real `entry_point` value — likely a tiny committed stub the bundle ships, or the field the pinned v0.3 spec actually requires for npx-shell-out servers), state how `user_config` values reach the process env, and add a Local criterion `npx -y @anthropic-ai/mcpb pack <dir> /tmp/lumen.mcpb` succeeds (npx only, no devDep change).

### F4 — no mechanism keeps the committed `server.json` (and therefore the `registry` print payload) version current after v0.3.0; I6's "not a version lie" holds only until the next release
- **Locations:** spec `IMPLICIT_SPEC_B1_release_train.md` I6; `PLAN_B1_release_train.md` Phase 3 (`version: 0.3.0 (tag-substituted runner-local at publish)`), Phase 2 (`registry` → pretty-printed `server.json` "as shipped", constants must equal the file), Phase 5 registry job (substitutes a runner-local copy — the committed file is never touched), Phase 1 (PR-template checkbox covers CHANGELOG only); runbook `docs/distribution.md` step list (D1 → tag → verify npm → registry check → mcpb install → directories → smoke) contains no version-bump step.
- **Why it fails:** runner-local substitution fixes the registry copy, but the committed `server.json` version and the anti-drift-pinned `registry` print payload stay at 0.3.0 forever. After v0.4.0 ships, `lumen mcp --print registry` from the installed CLI prints a stale version — the PRD E0.3 FR-5 promise ("prints `server.json` ... the onboarding code stays the single source of truth") becomes a lie, in tension with I4/P-Honest. I3 only forbids *runner* commits; a human release-prep bump is fully compatible and is simply missing from the plan.
- **Fix (plan amendment):** add "bump `server.json` version (and plugin/marketplace version)" to the release-prep discipline (Phase 1 checkbox or runbook step, as a human commit), keeping the runner-local substitution as the safety net; acknowledge the payload-staleness consequence explicitly.
